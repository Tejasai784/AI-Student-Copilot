Proactive UX (important): the app should feel
intelligent, not just menus. The dashboard greets by
time of day, states available time, flags the
approaching exam, and recommends 2–4 concrete
next actions with durations (e.g. "Revise recursion —
35 min"), each launching directly into the relevant flow.
Recommendations come from real data (weak topics,
plan, exam dates) — never hard-coded placeholders.

7A. VISUAL DESIGN DIRECTION
(the interface must look designed,
not templated)
The goal is a distinctive, premium product with its own
identity — not a default admin-template look.
Everything below is a starting proposal: follow it unless
I give different preferences, and record any change in
DECISIONS.md .
Concept: "a calm, focused study studio." Quiet
surfaces so the student's work is the loudest thing on
screen; one memorable element per page; color that
carries meaning (subject, mastery, urgency), not
decoration.

Subject colors: each subject gets its own color,
chosen by the student, reused across planner,

Avoid: gradient washes as decoration, a cream-
and-terracotta look, near-black with a neon
accent, purple-blue "AI gradient" backgrounds.
Typography (self-host via @fontsource, no CDN
dependency): headings Bricolage Grotesque ;
UI/body Figtree ; code JetBrains Mono . Defined
type scale (≈1.2 ratio), real weights, tuned letter-
spacing on large headings, body line-height ≥1.5,
chat/prose line length ≤75 characters. Do not default
to Inter/Roboto/system fonts.
Shape and depth: vary radius by hierarchy (hero
panels larger, cards medium, inputs small, chips pill)
instead of one radius everywhere. Use tonal surfaces
and 1px borders for structure; reserve shadow for
things that float (menus, dialogs, command palette).

Dashboard memorable element: the "Today"
hero with a live progress ring and one clear
primary action. Everything else is secondary and
quieter.
Chat: single centered reading column (~720px),
minimal chrome. AI answers render as full-width
prose (not bubbles); the student's messages get a
subtle tinted bubble. Citations appear as small
numbered chips that open a sources side panel.
Agent trace is a collapsible timeline under the
answer. Composer floats at the bottom with
attach, stop, and status line.
Planner: calendar/timeline with drag-to-
reschedule, tasks colored by subject, completion
ring per day.

Data viz: direct labels instead of legends where
possible, restrained gridlines, the shared mastery
ramp, accessible contrast, tooltips with the "why"
behind every score. Do not ship default chart-
library styling.
Sidebar: icon + label, collapsible, grouped (Learn /
Practice / Track / Account); mobile uses a bottom
bar plus a sheet for the full menu.
Motion: one orchestrated moment on first dashboard
load (progress ring fills, today's tasks settle in once).
Otherwise motion only responds to the student's
action (completing a task, dragging, expanding,
saving, toast). No fade-and-slide on every section, no
hover animation on every card. Streaming text
appears smoothly without layout jump. Honor
prefers-reduced-motion .
Copy: sentence case, plain active verbs, buttons say
what they do ("Start study session", "Save changes")
and the confirmation uses the same word ("Saved").
Errors say what happened and how to fix it. Empty
states invite an action ("Upload your first material to
start asking questions"). No lorem ipsum, no filler, no
ALL-CAPS eyebrow labels over every heading, no
emoji used as icons.
Components: shadcn/ui  (Radix) is used only as
accessible unstyled primitives and must be restyled
to these tokens — never shipped with default

styling. One icon set (Lucide) with consistent stroke

Quality floor (every page): responsive at 360 / 768 /

8. PERFORMANCE
Async I/O in routes and provider calls; pagination on all
list endpoints; DB indexes verified with query plans for
hot paths; response caching where safe (e.g.
dashboard aggregates, provider health);
embedding/result caching; lazy-loaded routes and
code-splitting on the frontend; virtualized long lists;
debounced search; background document
processing. Add a short before/after note in docs/  for
measurable improvements.
9. ERROR HANDLING (every layer)
Frontend: error boundaries, toasts, retry buttons;
"AI service is temporarily busy. Retrying…".
Backend: structured errors with request IDs; no
raw traces for normal users.
AI: retry temporary failures; provider fallback;
never hide auth/config errors.
RAG: clear message when no relevant material
exists.
Developer diagnostics may show detailed (still
secret-free) errors to admins.
